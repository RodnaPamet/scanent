# scanent 0.15.0

Its tag is made by the auto-release workflow on `main`'s head once CI has
passed there, not by a person.

## What changed

- **A second scanner: integrations.** scanent is now one platform with
  several scanners ([Several scanners in one scanent](../design/scanners.md)).
  The new integrations scanner reads which third-party applications a
  directory has granted access to, and whether anybody owns those grants:
  - **Microsoft Entra ID**: service principals with their verified publisher,
    application owners, delegated grants, application permissions, and,
    only when asked, sign-in activity.
  - **Okta**: applications and their OAuth grants.
  - **GitHub**: the organisation's App installations with their
    permissions, and its webhooks, reported by host only.

  It raises a high-privilege grant (directory, mail, files, chat, calendar
  or site content, or any write; HIGH), an unverified publisher (HIGH), no
  owner (MEDIUM), unused for 90 days by default (LOW), and an empty
  inventory (HIGH; LOW for a GitHub organisation, which can genuinely have
  no apps). Where a product's documented API cannot answer a question
  (owner, publisher or last use for Okta and GitHub), the report says it is
  not concluded and why, and raises nothing. A permission the scanner does
  not know is listed, never classified.
- **Its own report.** `report.integrations.signed.json`, contract
  `scanent-integrations/1`, signed with the same key. The agent report keeps
  `inflect-agent-harness/4` and its file name.
- **The scanners the sources choose.** Configure agent sources, integration
  sources or both; a run writes one signed report per scanner it ran. An
  integrations-only run works on its own, and its page and PDF say first
  that the agent scanner did not run.
- **`doctor`, `hosts` and `diff`** are grouped by scanner; the page, the
  PDF and two new CSVs (`integrations.csv`, `integration-findings.csv`) carry
  the integrations results.
- **The contract package's tarball is attached to the release**, with its
  SHA-256, so it installs with no registry token
  ([contract.md](../contract.md#install-it-from-a-release-with-no-token)).
- **A previous run's files are read through one descriptor**, opened
  without following a link, so they cannot be swapped between being checked
  and being read. This closes the CodeQL alerts 0.14.0 shipped with.
- **A GitHub 403 that is a rate limit** (`x-ratelimit-remaining: 0` or
  `retry-after`) is reported as `RATE_LIMITED`, for the agent scanner's
  `cicd` source too.

## What has not been done

Read [Assurance status](../security-pack/assurance-status.md) before relying
on this release. In short:

- **The integrations scanner has never read a real directory.** Its readers
  are tested against imitations written from Microsoft's, Okta's and
  GitHub's documented responses.
- **Okta's own apps are recognised by internal names Okta does not
  document** (`saasure`, `okta_enduser`, `okta_browser_plugin`); the names
  come from a third-party guide. If they are wrong, those apps are reported
  like any other.
- **That a Read-only Administrator token may read Okta app grants** is from
  Okta's documentation and has not been tried against a live organisation.
- **No pilot at a client, no external penetration test, no 72-hour soak.**

## Known limits

The limits of 0.14.0 stand ([its notes](0.14.0.md#known-limits)). Also:

- Okta and GitHub expose no application owner, publisher check or last use
  in the documented APIs this version reads, so those three findings are
  raised for Entra only.
- Google Workspace is not read yet.
- The `inflect` output posts the agent report only; Inflect has no ingest
  for the integrations report yet.

## Upgrading

From 0.14.0: no change is needed for an agents-only configuration. To add
the integrations scanner, add `entra-integrations`, `okta-integrations` or
`github-integrations` sources (`scanent init` offers them); each needs the
read permissions listed in the [access guide](../access.md).
