# scanent 0.16.0

Its tag is made by the auto-release workflow on `main`'s head once CI has
passed there, not by a person.

## What changed

- **The integrations report is posted to Inflect.** Inflect has an ingest
  for it now: `POST /api/t/<tenant>/admin/agents/integration-scans`, beside
  the agent report's `harness-scans`. The `inflect` output posts each report
  to its own ingest, the agent report first, each with a key of its own:
  - **A second key, `integrationsApiKeyEnv`.** The `inflect` block gains an
    optional `integrationsApiKeyEnv`, naming the variable that holds an API
    key with the scope `admin:integrations_ingest` and no other. Inflect gives
    the two ingests different scopes, so the agent report's key does not post
    the integrations report, and the configuration refuses the same variable
    for both. The `_FILE` form works as for every credential. One signing key
    signs both reports, as before.
  - **Without it, the integrations report is not posted**, and the log says
    so once a run, at info (`integrations report not posted`).
  - **A named key that is not set stops the run before any source is read**,
    as a missing agent key does.
  - **A run of integrations sources alone can post.** It needs the
    integrations key and no agent key: `apiKeyEnv` is now optional, and
    required only where the agent report is posted or the register is read.
  - **A refused or failed integrations post is not a delivery.** The run's
    exit code is `FAILED` (1), as for a refused agent report; the log names
    the tenant's refusal code (`integrations report refused`, with `REPLAY`
    on a 409) or the error (`integrations post failed`), never the body. The
    agent report is posted whatever happens to the integrations report.
  - **The scheduled path posts both**, by the same rules. In the package's
    API, `scanAndPost` now returns each report's answer
    (`{ ok, agents, integrations }`) instead of the agent report's alone.
- **`doctor`** checks the integrations key's variable when it is configured
  (scope `inflect-integrations`, in the integrations scanner's group), and
  says, as `not applicable`, that the integrations report will not be posted
  when integrations sources and the `inflect` output are configured without
  it.
- **`init`**, when integrations sources and an Inflect tenant are chosen,
  asks for the variable NAME of the integrations key (default
  `INFLECT_INTEGRATIONS_KEY`), never its value: beside an agent source it
  first asks whether to post the integrations report at all; with
  integrations sources alone it asks whether to post to a tenant, and no
  longer refuses to. The answers file takes `inflect.integrationsApiKeyEnv`.
- **`hosts`** lists the tenant under the integrations scanner too when that
  report is posted. The [access guide](../access.md) has a section for the
  second key.

## What has not been done

Read [Assurance status](../security-pack/assurance-status.md) before relying
on this release. In short:

- **The integrations report has never been posted to a running Inflect
  tenant.** The post is tested against an imitation of Inflect's ingest
  written from its route and its refusal codes.
- **The integrations scanner has never read a real directory.** Its readers
  are tested against imitations written from Microsoft's, Okta's and
  GitHub's documented responses.
- **No pilot at a client, no external penetration test, no 72-hour soak.**

## Known limits

The limits of 0.15.0 stand ([its notes](0.15.0.md#known-limits)), except
that the `inflect` output now posts the integrations report. Also:

- Inflect's ingest for the integrations report needs an API key with the
  scope `admin:integrations_ingest`, a key other than the one that posts the
  agent report, and the report's signing key registered against the scanner
  agent the report names.
- Okta and GitHub expose no application owner, publisher check or last use
  in the documented APIs this version reads, so those three findings are
  raised for Entra only.
- Google Workspace is not read yet.

## Upgrading

From 0.15.0: no change is needed. A configuration without
`integrationsApiKeyEnv` posts what it posted before, and says in the log that
the integrations report was not posted. To post the integrations report, add
`"integrationsApiKeyEnv": "INFLECT_INTEGRATIONS_KEY"` (or a name of your
own) to the `inflect` block, and set that variable, or its `_FILE`, to a key
created on the tenant's API keys page with the scope
`admin:integrations_ingest` and no other. A configuration of integrations
sources alone may then use the `inflect` output, and may leave `apiKeyEnv`
out.
