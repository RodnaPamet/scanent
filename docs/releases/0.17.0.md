# scanent 0.17.0

Its tag is made by the auto-release workflow on `main`'s head once CI has
passed there, not by a person. 0.16.1 was prepared and never released; its fix
ships here.

## What changed

- **The agent-surface rules run in a scan, sign a report of their own, and
  post it to the tenant.**
  For each MCP tool the `mcp` source reads, static rules run over its
  description and the JSON of its input schema, each up to 65,536 characters.
  They are re-authored in TypeScript from Cisco AI Defense's `mcp-scanner`
  (Apache-2.0) and the Agent Threat Rules (MIT), and look for an attack written
  into the text: tool poisoning, prompt injection, an executable payload, an
  instruction to send data away or to take credentials. A rule that fires
  leaves the source as a code, the rule id, a severity, the tool and the field,
  never the text. The run signs these into `report.agent-rules.signed.json`
  under `scanent-agent-rules/1`, with the agent report's key and scan id.
  - "No finding" is said only of a complete read of at least one tool. A read
    that stopped, or a field longer than the cap, makes the population
    `INCOMPLETE`; what was read keeps its findings. A complete read of no tool
    is `NOTHING_READ`, never clean.
  - The report lists each origin it read — an MCP server, a code root — in
    full or in part, and each finding names its origin (`origins[]`,
    `originRef`), so a consumer closes a finding only when the same scanner
    read that origin in full and did not raise it again.
  - A finding is HIGH at most (MEDIUM for most codes), a suggestion a person
    confirms, and never changes an agent's level.
  - The file output writes the report, `agent-rule-findings.csv`, an
    `agentRules` section of `results.json`, and an "Agent surface" section of
    `summary.html` and of `report.pdf`. `stdout` prints the report after the
    agent report.
  - The `inflect` output posts it to
    `/api/t/<tenant>/admin/agents/agent-rule-scans` with a key of its own,
    named by `inflect.agentRulesApiKeyEnv` and holding `admin:agent_rules_ingest`
    and no other scope. Without that key it is not posted, and the log says so
    once. `init` offers the key when an `mcp` source is answered, and `doctor`
    checks it under `inflect-agent-rules`.
  - The rules themselves make no request.
- **The agent-surface rules read agent skills.** The `code` source now reads
  each `SKILL.md` under its roots — its front matter and its instructions — and
  every script in the skill's directory down to the next skill (shell,
  PowerShell, batch, Python, JavaScript and TypeScript, Ruby, Perl, PHP), for
  the agent-surface rules alone: nothing it finds enters the agent report.
  - 25 skill rules, re-authored from Cisco AI Defense's `skill-scanner`
    (Apache-2.0) and the Agent Threat Rules (MIT), raise six codes:
    `SKILL_PROMPT_INJECTION` (an instruction to set the rules aside, a
    chat-template role token, a payload in an HTML comment, runs of invisible
    characters, concealment from the user), `SKILL_COMMAND_INJECTION` (a
    reverse shell, a decoded command run, a download run from a raw address or
    a paste service, a destructive command), `SKILL_DATA_EXFILTRATION`,
    `SKILL_CREDENTIAL_HARVESTING`, `SKILL_EXCESSIVE_PERMISSION` (`Bash(*)` in
    `allowed-tools`, approval turned off, an agent's own memory or settings
    rewritten) and `SKILL_IMPERSONATION`. Each rule reads only its kinds: the
    instruction rules read `SKILL.md`, never a script's comments.
  - Each code root is an origin, `code:<root label>`, read in full or in part
    with its reason, like a server.
  - On by default; `"skills": false` on a `code` source turns it off. So a
    code-only scan now signs the agent-rules report too: `stdout` prints two
    reports, and a run writes nine files. The offline example gains a small
    clean skill, so its section reads "No rule fired".
- **The runtime base moves to a distroless build carrying `libc6`
  `2.41-12+deb13u5`**, which fixes CVE-2026-19499 and CVE-2026-5435 (High) and
  twelve lesser CVEs in `deb13u4`. The Grype gate refused every image on the
  earlier base; the owner chose to wait for the patched build rather than
  allowlist them, and 0.17.0 was held until it shipped.
- **An Agent SDK agent under `permissionMode: "dontAsk"` is reported with
  the tools it can call, not every tool its servers offer** (issue 33). The
  `code` source reported each MCP server an agent's options configure as
  `<server>:*`, because `allowedTools` only approves and does not restrict.
  That is true in the SDK's default mode. Under `dontAsk` the SDK denies
  every call nothing pre-approved, and only `allowedTools`, an allow rule in
  a settings file and a PreToolUse hook can pre-approve one. So when the
  options are read whole, `allowedTools` is read whole with no unanchored
  `*` or `mcp__*`, `settingSources` is `[]` and there is no hook, the agent's
  tools are now what `allowedTools` approves:
  - built-ins it does not name are dropped;
  - a server stays `<server>:*` only when it is approved whole
    (`mcp__<server>__*`, another glob after that prefix, or a bare
    `mcp__<server>`);
  - the shell-or-fetch option is judged on the narrowed built-ins.

  Any condition that fails, or that the reader cannot read, keeps the tools
  as configured. Inflect's own connect-wizard snippet is the case that found
  it: it was reported as able to call every tool of its Inflect server, and
  Inflect raised one HIGH unpinned-write finding on it. It is now reported
  with the one tool it is approved for.

## What has not been done

Read [Assurance status](../security-pack/assurance-status.md) before relying
on this release. In short:

- **The rules have been checked against their own corpus only**: every planted
  case fires its rule and no clean case fires any. They have not been run
  against a real MCP server whose tools are known to be poisoned, nor a real
  malicious skill. Over one real skill, Cloudflare's security-audit skill
  (vendored in this repository), whose reference files describe attacks at
  length, no rule fires.
- **The dontAsk narrowing is read from the SDK's documentation**, and tested
  against fixtures written to it. It has been checked against one real agent,
  the connect-wizard snippet that found it.
- **No pilot at a client, no external penetration test, no 72-hour soak.**

## Known limits

The limits of 0.16.0 stand ([its notes](0.16.0.md#known-limits)). Also:

- **The rules are patterns.** A tool that describes reading a file or calling
  a URL for a legitimate reason can match one, and a poisoning written in
  words no rule names is missed, as is one spelt to dodge them (a line split
  across a continuation, another language). Server-level instructions are not
  read yet, nor are A2A agent cards, nor the files a skill bundles beyond
  `SKILL.md` and its scripts (reference Markdown, data).
- **The agent-rules report reaches Inflect only once the tenant runs a build
  with its ingest.**
- An endpoint-managed policy loads whatever the code says and can add allow
  rules. Code cannot see it, so a narrowed tool set is what the code allows,
  not a statement about the machine that runs the agent.

## Upgrading

From 0.16.0: no change is needed. A run with an `mcp` or a `code` source writes
two more files and prints a second report on `stdout`, and its `results.json`
gains an optional `agentRules` section that a reader of 0.16.0's results may
ignore. A reader of `stdout` that took one line as one report reads the first
line, or sets `"skills": false` on a code-only configuration to keep one. To post the agent-rules report, create a
key with `admin:agent_rules_ingest` and name its variable as
`inflect.agentRulesApiKeyEnv`. A consumer that pinned the 0.16.0 manifest hash
pins the new one.
