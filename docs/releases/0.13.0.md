# scanent 0.13.0

**Tagged and never published.** The release run for `v0.13.0` failed at
the first image push, before anything was pushed, signed or attached to a
release. The same code is released as [0.13.1](0.13.1.md), which says why.
These notes are kept as they were written for the tag.

The first release of scanent, the Agent Estate Scanner. Its tag is made by
the auto-release workflow on `main`'s head once CI has passed there, not by a
person.

scanent reads an organisation's agent sources with read-only credentials,
lists the AI agents and agent-shaped identities it finds, scores each on a
ladder of six levels, and writes a signed report, two spreadsheets and one
page to open in a browser. It runs inside the organisation and sends nothing
anywhere unless it is configured to.

## What is released

- The image `ghcr.io/rodnapamet/scanent:0.13.0`, for linux/amd64 and
  linux/arm64, signed by this repository's release workflow, with a CycloneDX
  SBOM and build provenance attached.
- The air-gapped bundle `scanent-0.13.0-airgap.tar`: both images, their
  SBOMs, the Helm chart, the Compose files, the documents, and a signed list
  of checksums.
- The report contract as an npm package on GitHub Packages:
  `@rodnapamet/scanent-contract@0.13.0`.

[Verify a release](../verify-a-release.md) has the commands that check each
of them. This is the first time any of them has been signed or published, so
it is also the first time those commands can be run against a real release.

## The declared surface

Every request the scanner can make is declared in the code, and a hash of
that declaration is in every report. For 0.13.0 it is

`sha256:b3f849ccdc10031f2d2e8aa6a0acd02b96843f7be71699a894288f07a7fcdf0a`

There is no earlier release to compare it with. A report that carries
another hash was not made by this version.

- CI on Node 22 and Node 24, the image scans (Trivy and Grype), the cluster
  install on kind, CodeQL and Scorecard, on the commit that was tagged.
- The long tests, by hand, at commit `8388ff0`: https://github.com/RodnaPamet/scanent/actions/runs/43356834306
- The release workflow, by hand, at commit `8388ff0`, which builds and tests
  everything and signs and publishes nothing: https://github.com/RodnaPamet/scanent/actions/runs/43356838356
  Its first run, a day earlier, found one defect in the workflow itself (the
  SBOM step wrote into a directory that did not exist), which was fixed.
- A soak: a 75-minute soak was run on 2026-11-13 at commit `7437554`: 75 scans, one a minute, none failed and none started late (the latest by 64 ms), and resident memory was 110 MiB after the first scan and 110 MiB after the last. The two commits after
  that one change how two runs are compared, how the tests are started, and
  documents; what the soak runs is the same.
- One pilot, on 2026-11-12, on the estate of Inflect Ltd., which makes
  scanent. Four live sources (Microsoft Entra ID, GitHub Actions, Google
  Cloud and an Inflect register) were read in full in 14 seconds, and one
  repository of 7,539 source files was scanned. The scanner this one was

## What has not been done

Read [Assurance status](../security-pack/assurance-status.md) before relying
on this release. In short:

- **No pilot at a client.** The one pilot was on the maker's own estate.
  Okta, Azure Key Vault, LangSmith and MCP servers have never been read for
  real: those readers are tested against imitations of each product's API.
- **False positives and false negatives are not measured.**
- **No external penetration test and no independent code review.**
- **No 72-hour soak.** It is required before 1.0.
- **The signing and publishing steps had never run before this tag.** If
  something in them is wrong, it is fixed forward in 0.13.1; a version is
  never released twice.

## Known limits

- The scanner cannot tell which automated identities run a model. A
  principal that is on no list and shows no sign of one is reported as an
  unregistered automated identity, at MEDIUM, and is not held to the agent
  bar. On the pilot estate that was 34 of 40 principals: CI workflows that
  hold a credential, service accounts and service principals. A workflow
  that calls a model through a key it holds shows no sign the scanner reads,
  so it is reported the same way (issue 25).
- The code source recognises LangChain, LangGraph and the Claude Agent SDK,
  and a model call that is given tools on the Anthropic, OpenAI and Azure
  OpenAI, Google Gemini and AWS Bedrock SDKs. An agent written with another
  framework, or on another provider's SDK, is not found in code. An agent
  whose tools another file builds is reported with its tools not known, and
  the code source then reads as incomplete and names the line. Recognition
  of provider SDKs is tested against fixtures written from the SDKs' own
  type definitions and one real repository; it has not been run on a
  client's code.
- Okta API tokens that belong to other users may not be seen by a Read-only
  Administrator, and the report cannot say so (issue 16).
- `doctor` can show that a credential is able to write for Entra and for a
  GitHub classic token only (issue 19).
- The NVIDIA OpenShell source is not usable in this release.

## Upgrading

There is no earlier release. A configuration, an inventory or a results file
made by an unreleased build may be refused; `docs/scanner.md`, under "Changes
that can stop a setup that scanned before", says what changed.
